## Objetivo e aceite

Encaminhar `/api` do Vite para Express em desenvolvimento e, em produção local, servir a API e o build SPA pelo mesmo processo. Verificar `/api/health`, acesso direto a rotas da SPA e JSON 404 para API inexistente, sem esconder falhas de ativos como HTML.

## Arquitetura

Contexto consultado: tarefa 1.2 e seguinte 1.3 em `tasks.md`; decisões 1, 2 e 7 em `design.md`; contratos funcionais e restrição de entrada misteriosa da spec `terminal-entry`; bootstrap existente em `api/src/app.js`, `web/vite.config.js` e manifests. O escopo é infraestrutura: preserva-se o componente React atual, sem menus ou novos fluxos visuais.

**Desenvolvimento:** configurar em `web/vite.config.js` o proxy com chave `/api` e destino local explícito do processo Express, preservando o prefixo. Evitar reescritas ou CORS: o navegador requisita a mesma origem Vite e o proxy encaminha ao servidor. Criar script para iniciar a API de forma separada e documentar os dois terminais e endereços; `npm run dev` atual continua iniciando Vite. Manter o serviço local previsível para o proxy; configuração abrangente por ambiente é 1.3.

**API e produção:** manter a fábrica `createApp` importável sem abrir porta, e colocar `listen` em módulo de entrada dedicado. Registrar `GET /api/health`, retornando JSON mínimo, sem configurações ou conteúdo pessoal. Encaminhar todas as demais requisições sob `/api` para um handler JSON 404, inclusive `/api` e métodos diferentes, antes de estáticos ou fallback. Definir o caminho absoluto de `web/dist` a partir da localização do módulo (`import.meta.url`/`fileURLToPath`), não do diretório de trabalho, para funcionar tanto pela raiz quanto pelo workspace em Windows.

Em produção, `express.static` entrega arquivos reais. O fallback é um middleware de leitura limitado a GET/HEAD que aceite explicitamente `text/html` em `Accept`, após o tratamento de `/api`, sem usar a rota curinga incompatível com a sintaxe de Express 5. Arquivos ausentes, pedidos de assets e requisições que não pedem HTML recebem 404, não `index.html`; uma navegação direta como `/nexo/novo` com `Accept: text/html` recebe o HTML da SPA. Não servir arquivos-fonte nem criar endpoints de negócio. Tratar falha de build ausente de modo explícito e sem alegar que a SPA foi entregue.

O servidor pode usar porta e modo mínimos para operar nesta etapa; sua validação integral, `APP_ORIGIN`, `DATABASE_PATH`, `SESSION_SECRET`, diretório de dados, scripts de migração e testes pertencem à tarefa 1.3. Não antecipar configurações de autenticação, persistência ou HTTPS de produção. Documentar o limite temporário para que o tutorial não confunda a verificação de produção local da 1.2 com implantação segura do piloto.

**Alternativas:** servir frontend e API em domínios diferentes introduziria configuração de origem/cookies não prevista; redirecionar toda requisição 404 para `index.html` esconderia erros de API e arquivos; `process.cwd()` quebraria com outra pasta de inicialização; importar o módulo do servidor para construir a aplicação abriria porta como efeito colateral. A separação de fábrica e entrada evita esses problemas.

**Arquivos previstos:** `api/src/app.js`, entrada do servidor sob `api/src/`, `api/package.json`, `package.json` quando necessário, `web/vite.config.js`, README, registro/tutorial/índice e marcação final da tarefa. Não introduzir dependências desnecessárias. O código exato e sua ordem de execução devem ser explicados no tutorial.

**Critérios observáveis:** (1) executar build real e iniciar Express em modo de produção local; `GET /api/health` responde 200 JSON; (2) `/api/inexistente`, `/api` e método inválido de API retornam 404 JSON, inclusive com `Accept: text/html`; (3) navegação direta `/nexo/novo` com `Accept: text/html` recebe `index.html`, enquanto URL de arquivo inexistente e requisição sem aceitação explícita de HTML recebem 404; (4) carregar recursos reais do build e a página inicial em navegador; (5) iniciar Vite e API e confirmar, por requisição ao endereço Vite, que `/api/health` passa pelo proxy; (6) executar uma verificação a partir de diretório de trabalho diferente para confirmar resolução do build; (7) registrar portas, comandos, respostas reais e limitações, conferir tutorial e commit. Testes automatizados pequenos que exercitem os contratos HTTP têm valor, desde que não substituam a verificação do build e do navegador.

**Sequência com 1.3:** 1.2 entrega servidor e proxy operantes com a configuração mínima documentada; 1.3 substitui essa configuração por validação central de `NODE_ENV`, `PORT`, `APP_ORIGIN`, `DATABASE_PATH` e `SESSION_SECRET`, adiciona scripts e documentação de ambiente e testa falhas. A integração deve preservar os contratos HTTP já verificados na 1.2. Os requisitos de produção de 1.3 não devem ser reivindicados antes da sua implementação.

## Verificações e evidências

Windows, PowerShell, Node portátil 24.22.3 e npm 11.19.1. Na raiz, `npm.cmd run build` compilou 16 módulos. Em produção local, `$env:NODE_ENV='production'; node api/src/server.js` iniciou na porta 3000. Usando `fetch` real do Node:

| Requisição | Resultado observado |
| --- | --- |
| GET `/api/health` | 200 JSON `{"status":"ok"}` |
| GET `/api/inexistente` e `/api` com `Accept: text/html` | 404 JSON com código `NOT_FOUND` |
| POST `/api/health` com `Accept: text/html` | 404 JSON |
| GET `/nexo/novo` com `Accept: text/html` | 200 HTML da SPA |
| GET `/ausente.js` com `Accept: text/html` | 404, sem fallback SPA |
| GET `/nexo/novo` sem aceitação explícita de HTML | 404 |
| GET `http://127.0.0.1:5173/api/health` via Vite | 200 JSON da API |

Para o proxy, `npm.cmd run dev --workspace=@nexo/web -- --host 127.0.0.1 --port 5173 --strictPort` iniciou Vite; a API de produção estava ativa em 3000. Tentativa anterior de encaminhar esses argumentos pelo script da raiz falhou porque o script aninhado não repassa flags; a verificação usou diretamente o workspace. O README recomenda o script da raiz sem argumentos.

Em `TEMP`, importando `api/src/app.js` por caminho absoluto, `createApp({production:true})` serviu `/nexo/novo` com 200 HTML, confirmando independência do diretório de trabalho. Ambos os servidores foram encerrados. A inspeção visual em navegador cabe ao gerente; o teste HTTP não a substitui.

Após combinar o teste de aceitação explícita com a negociação do Express, uma instância temporária na porta dinâmica confirmou: `Accept: text/html` retorna 200 para `/nexo/novo`; `Accept: text/html;q=0` e `Accept: */*` retornam 404. `git diff --check` passou, com avisos de normalização de finais de linha do Git.
