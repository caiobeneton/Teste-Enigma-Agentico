# 1.1 — Construir a base JavaScript com React, Vite e Express

## O que vamos construir

Neste capítulo, você criará os arquivos da primeira base executável do Nexo: uma página React que mostra **“O que você busca?”**, compilada pelo Vite, e uma fábrica que cria uma aplicação Express vazia. Aprenderá a organizar dois pacotes no mesmo repositório, fixar dependências e conferir instalação, compilação e importação.

O ponto de partida é `76b8d64750c3c2f3aa3554a5da3afe4e61c93d69`. Nesse commit existem o planejamento e o processo educacional, mas nenhum código da aplicação. Leia primeiro [PROC-01](../PROC-01.md) para entender os papéis da equipe. A origem deste capítulo é a [tarefa 1.1](../../../openspec/changes/define-puzzle-platform-mvp/tasks.md); decisões e evidências estão no [registro correspondente](../../registros/define-puzzle-platform-mvp/1.1.md).

## Passo 1 — Preparar Node e uma cópia de estudo

Todos os comandos usam **PowerShell no Windows x64**, partindo da raiz do repositório. Você precisa de Git, um editor que salve UTF-8, acesso ao registro npm e Node **24.22.3**, referência usada nesta entrega. O npm incluído na distribuição verificada é **11.19.1**. As versões são uma referência histórica deste capítulo, não uma promessa de atualização automática.

Node executa JavaScript fora do navegador. npm instala pacotes e executa os comandos declarados no projeto. A máquina da entrega tinha Node global 24.11.1, que será rejeitado pela faixa configurada aqui. Para usar a referência sem substituir a instalação global, obtenha a [distribuição oficial Node 24.22.3](https://nodejs.org/dist/v24.22.3/) e seus [checksums SHA256](https://nodejs.org/dist/v24.22.3/SHASUMS256.txt).

O roteiro abaixo baixa somente o ZIP Windows x64 e o arquivo de checksums para uma pasta temporária:

```powershell
$nodeVersao = '24.22.3'
$nodePastaBase = Join-Path $env:TEMP "nexo-node-$nodeVersao"
$nodeArquivo = "node-v$nodeVersao-win-x64.zip"
$nodeZip = Join-Path $nodePastaBase $nodeArquivo
$nodeSomas = Join-Path $nodePastaBase 'SHASUMS256.txt'
New-Item -ItemType Directory -Force -Path $nodePastaBase | Out-Null
curl.exe --fail --location --output $nodeZip "https://nodejs.org/dist/v$nodeVersao/$nodeArquivo"
if ($LASTEXITCODE -ne 0) { throw 'Falha no download do Node.' }
curl.exe --fail --location --output $nodeSomas "https://nodejs.org/dist/v$nodeVersao/SHASUMS256.txt"
if ($LASTEXITCODE -ne 0) { throw 'Falha no download dos checksums.' }
$linhaSoma = Get-Content -LiteralPath $nodeSomas | Where-Object { $_ -match ('\s+' + [regex]::Escape($nodeArquivo) + '$') }
if (@($linhaSoma).Count -ne 1) { throw 'Checksum unico nao encontrado.' }
$somaEsperada = ($linhaSoma.Trim() -split '\s+')[0].ToLowerInvariant()
$somaObtida = (Get-FileHash -Algorithm SHA256 -LiteralPath $nodeZip).Hash.ToLowerInvariant()
if ($somaObtida -ne $somaEsperada) { throw 'Checksum diferente: nao extraia este arquivo.' }
Expand-Archive -LiteralPath $nodeZip -DestinationPath $nodePastaBase -Force
$nexoNodeDir = Join-Path $nodePastaBase "node-v$nodeVersao-win-x64"
$env:PATH = "$nexoNodeDir;$env:PATH"
$env:npm_config_cache = Join-Path $env:TEMP 'nexo-npm-cache-1-1'
node --version
npm.cmd --version
```

SHA256 produz uma impressão digital do arquivo: a comparação detecta diferenças entre o ZIP recebido e o checksum publicado pela fonte oficial. O ZIP conferido nesta entrega teve SHA256 `e612af99f626ab415ea225af6bce5c971feb448cb5cae250bb1c3fa50c5f7d9f`. As saídas finais devem ser `v24.22.3` e `11.19.1`.

`$env:PATH` foi alterado somente nesta sessão do PowerShell e seus subprocessos. O cache npm também fica temporário. O arquivo `.nvmrc` que criaremos não instala o Node e não ajusta o PATH sozinho. Usamos `npm.cmd` explicitamente para executar o lançador Windows, evitando confusão com `npm.ps1` e a política de execução de scripts.

Se o download pelo terminal falhar por TLS ou configuração de rede, use os links oficiais no navegador e salve os mesmos dois arquivos nos caminhos indicados; prossiga a partir de `$linhaSoma`. Não pule a conferência nem altere a instalação global. Se a pasta portátil já estiver preparada e verificada, basta definir `$nexoNodeDir`, ajustar o PATH e conferir as versões.

Agora crie uma cópia de estudo com o histórico, em uma pasta nova, para não sobrescrever arquivos do seu projeto:

```powershell
$origemProjeto = (Get-Location).Path
$pastaEstudo = Join-Path $env:TEMP ('nexo-aula-1-1-' + [guid]::NewGuid().ToString('N'))
git clone --no-hardlinks -- $origemProjeto $pastaEstudo
if ($LASTEXITCODE -ne 0) { throw 'Falha ao criar a copia de estudo.' }
Set-Location -LiteralPath $pastaEstudo
git switch --detach 76b8d64750c3c2f3aa3554a5da3afe4e61c93d69
if ($LASTEXITCODE -ne 0) { throw 'Commit-base indisponivel.' }
New-Item -ItemType Directory -Force -Path web/src, api/src | Out-Null
```

`switch --detach` posiciona somente essa cópia no commit-base, sem mover uma branch da origem. Mantenha o PowerShell aberto para preservar o PATH de sessão. Nos próximos passos, **crie cada arquivo no caminho indicado e copie seu conteúdo integral**. Os blocos não contêm reticências nem dependem de um gerador de projeto.

## Passo 2 — Declarar a raiz e as regras de instalação

### Arquivo `package.json`

```json
{
  "name": "nexo",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "workspaces": [
    "web",
    "api"
  ],
  "engines": {
    "node": ">=24.22.3 <25"
  },
  "scripts": {
    "dev": "npm run dev --workspace=@nexo/web",
    "build": "npm run build --workspace=@nexo/web",
    "preview": "npm run preview --workspace=@nexo/web"
  }
}
```

Um `package.json` é o manifesto de um pacote: declara identidade, requisitos e comandos. `private: true` impede a publicação acidental desse pacote no npm. `version: "0.0.0"` identifica esta base inicial, sem anunciar uma versão pública.

**Workspaces** são pacotes locais gerenciados pelo mesmo projeto npm. `web` e `api` terão manifests próprios, uma instalação pela raiz e um lockfile compartilhado. A opção `--workspace=@nexo/web` direciona os comandos para o pacote de frontend, cujo nome declararemos a seguir. Isso evita ter que mudar de pasta para cada operação. Consulte a [documentação de workspaces npm](https://docs.npmjs.com/cli/v11/using-npm/workspaces/).

`type: "module"` escolhe módulos ES para arquivos `.js`: usaremos `import` e `export`. Cada pacote declara isso explicitamente, inclusive a API. `engines` aceita Node a partir de 24.22.3 e abaixo de 25; a regra não garante que um patch permaneça atualizado no futuro.

### Arquivo `.npmrc`

```ini
save-exact=true
engine-strict=true
```

`save-exact` orienta futuras inclusões de dependências a registrar versões exatas, sem `^` ou `~`. `engine-strict` faz o npm rejeitar runtimes que não satisfaçam os manifests. Portanto, Node 24.11.1 não é um ambiente válido para instalar este capítulo. Essa configuração governa o gerenciador de pacotes; ainda não configura variáveis da aplicação.

### Arquivo `.nvmrc`

```text
24.22.3
```

Ele registra a versão de referência para pessoas e ferramentas compatíveis. Não é um programa de instalação; por isso conferimos o runtime no passo anterior.

### Arquivo `.gitignore`

```gitignore
node_modules/
web/dist/
npm-debug.log*
```

`node_modules/` contém dependências instaláveis, `web/dist/` conterá o build e os logs npm são saídas locais. Esses arquivos não precisam entrar no Git. Os manifests e `package-lock.json` devem ser versionados: são a receita para reconstruir a instalação. Dados, segredos e ambiente da aplicação serão tratados quando existirem nas tarefas correspondentes.

**Como conferir:** os quatro arquivos estão na raiz, e não dentro de `web`. JSON usa aspas duplas e não aceita vírgula depois do último item de uma lista ou objeto.

## Passo 3 — Definir o pacote do frontend e o plugin React

### Arquivo `web/package.json`

```json
{
  "name": "@nexo/web",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "engines": {
    "node": ">=24.22.3 <25"
  },
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  },
  "dependencies": {
    "react": "19.3.1",
    "react-dom": "19.3.1"
  },
  "devDependencies": {
    "@vitejs/plugin-react": "6.3.0",
    "vite": "8.3.8"
  }
}
```

`@nexo/web` é o nome local com um escopo (`@nexo`), usado nos comandos da raiz. Ele continua privado. React descreve componentes; React DOM conecta esses componentes ao DOM, a árvore de elementos que o navegador apresenta. Fixamos ambos em 19.3.1 para manter a combinação escolhida.

`dependencies` declara bibliotecas utilizadas pela aplicação. `devDependencies` declara ferramentas para desenvolver e gerar o resultado: aqui, Vite e seu plugin React. No frontend compilado, o navegador recebe os arquivos produzidos, não executa o comando Vite. Contudo, para **construir** esse resultado é necessário instalar também as dependências de desenvolvimento; não use uma instalação com `--omit=dev` antes do build.

Vite oferece um servidor de desenvolvimento e um comando de compilação. `dev` inicia o primeiro, `build` gera arquivos estáticos e `preview` permite inspecioná-los localmente. Ele não substitui o servidor Express integrado que será criado depois. Veja o [guia oficial do Vite](https://vite.dev/guide/).

### Arquivo `web/vite.config.js`

```javascript
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
});
```

`defineConfig` explicita o objeto de configuração. `react()` ativa a integração React: transformação JSX e Fast Refresh durante o desenvolvimento. JSX é a sintaxe parecida com HTML que escreveremos dentro do JavaScript; a ferramenta a transforma em JavaScript executável. Não configuramos outro compilador, TypeScript, roteamento ou proxy, pois não são necessários para montar esta primeira página.

## Passo 4 — Ligar HTML, React e estilo

### Arquivo `web/index.html`

```html
<!doctype html>
<html lang="pt-BR">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <link rel="icon" href="data:," />
    <title>Nexo</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
```

`lang="pt-BR"` identifica o idioma; UTF-8 preserva acentos; `viewport` instrui o navegador a usar a largura do dispositivo. O elemento `root` será o ponto de montagem do React. `type="module"` carrega a entrada como módulo e permite suas importações.

O favicon é o pequeno ícone da aba. `href="data:,"` declara um ícone vazio embutido: não cria uma marca visual, mas evita a busca automática por um arquivo `/favicon.ico` inexistente. Ele foi acrescentado após o gerente observar esse 404 no navegador, e o build foi recompilado e inspecionado novamente.

### Arquivo `web/src/main.jsx`

```jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import App from "./App.jsx";
import "./styles.css";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>,
);
```

`getElementById("root")` encontra o elemento do HTML. `createRoot` cria uma raiz React para ele, e `render` apresenta a árvore de componentes. A importação CSS permite ao Vite processar e entregar o estilo junto da aplicação.

`StrictMode` ativa verificações adicionais durante o desenvolvimento, como novas execuções que ajudam a encontrar renderização impura e limpezas ausentes. Ele não cria um elemento visual nem duplica a tela de produção; essas verificações são próprias do desenvolvimento. Veja a [referência do StrictMode](https://react.dev/reference/react/StrictMode).

### Arquivo `web/src/App.jsx`

```jsx
export default function App() {
  return (
    <main>
      <h1>O que você busca?</h1>
    </main>
  );
}
```

Um componente React é uma função que descreve a interface retornada. O nome começa com maiúscula para que `<App />` seja reconhecido como componente. `export default` permite importá-lo na entrada. `<main>` identifica o conteúdo principal e `<h1>` seu título. Ainda não há um campo de resposta: criar um controle aparentemente funcional sem comportamento real confundiria o resultado desta tarefa.

### Arquivo `web/src/styles.css`

```css
:root {
  font-family: Consolas, "Courier New", monospace;
  color: #e8e8e8;
  background: #121212;
  font-synthesis: none;
  text-rendering: optimizeLegibility;
}

body {
  margin: 0;
}

main {
  padding: 2rem;
}

h1 {
  margin: 0;
  font-size: 1.25rem;
  font-weight: 400;
  line-height: 1.5;
}
```

`:root` aplica a base tipográfica e as cores ao documento. A lista de fontes fornece alternativas monoespaçadas: se Consolas não existir, o navegador tenta a próxima. `font-synthesis: none` evita variações artificiais da fonte, enquanto `text-rendering` expressa preferência de legibilidade.

Removemos a margem padrão de `body` para controlar o espaço com `main`. A unidade `rem` é relativa ao tamanho de fonte da raiz: `2rem` cria afastamento do conteúdo; `1.25rem` define o título. `line-height` melhora seu espaçamento vertical. Isso oferece um estilo mínimo legível, sem antecipar todos os estados ou critérios da interface futura.

**Como conferir a ligação:** HTML carrega `main.jsx` → entrada importa `App` e CSS → React monta `App` dentro de `root`. Um caminho ou identificador divergente quebra essa ligação.

## Passo 5 — Criar uma fábrica Express sem iniciar servidor

### Arquivo `api/package.json`

```json
{
  "name": "@nexo/api",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "engines": {
    "node": ">=24.22.3 <25"
  },
  "dependencies": {
    "express": "5.3.0"
  }
}
```

Express é uma biblioteca do servidor, por isso aparece em `dependencies` da API. O pacote declara ESM e o mesmo requisito de Node para que os dois workspaces tenham uma referência comum. Não há um script `build` artificial: o Node executa este JavaScript diretamente.

### Arquivo `api/src/app.js`

```javascript
import express from "express";

export function createApp() {
  return express();
}
```

Uma **fábrica** é uma função que cria e devolve uma instância. `createApp` retorna uma aplicação Express nova a cada chamada. Separar criação da aplicação e abertura de uma porta permitirá configurar e verificar a aplicação sem iniciar um processo HTTP ao importar o módulo.

Este arquivo ainda não chama `listen`, não define rotas e não acessa banco. Isso mantém o contrato pequeno: importar e criar a instância deve funcionar sem efeitos externos. A existência da dependência no manifesto, sozinha, não provaria isso; faremos uma importação real no próximo passo.

Até aqui, você escreveu 12 arquivos de código/configuração. O 13º arquivo manual da entrega é o [README da raiz](../../../README.md), que documenta comandos e estado atual; leia-o e atualize a cópia de estudo com essas instruções de uso e seus limites. O `package-lock.json`, por sua vez, será gerado pelo npm, não escrito manualmente.

## Passo 6 — Instalar e entender o lockfile

Na raiz da cópia de estudo, confira novamente o Node e instale:

```powershell
node --version
npm.cmd --version
npm.cmd install
if ($LASTEXITCODE -ne 0) { throw 'A instalacao falhou.' }
npm.cmd ls --workspaces --depth=0
```

O npm lê a raiz, encontra `web` e `api`, instala suas dependências e cria os vínculos locais dos workspaces. Você deve ver Express 5.3.0 em `@nexo/api`; React/React DOM 19.3.1, Vite 8.3.8 e plugin React 6.3.0 em `@nexo/web`.

A instalação gera um único `package-lock.json` na raiz. Os manifests fixam as dependências **diretas** que escolhemos. Elas também dependem de outros pacotes, chamados dependências **transitivas**, que podem declarar faixas próprias. O lockfile registra a árvore resolvida e dados de integridade. Portanto, mesmo com versões diretas exatas, uma primeira instalação sem lockfile feita no futuro pode resolver transitivas diferentes.

Para reconstruir **a árvore exata desta entrega**, use o lockfile dela e `npm ci`. Não escreva o lockfile à mão nem restaure a implementação inteira no lugar de criar os arquivos ensinados. Depois que a entrega tiver sido commitada, na cópia de estudo que contém seu histórico:

```powershell
$commitEntrega = git log --all -1 --format=%H --grep='^Task: define-puzzle-platform-mvp/1.1$'
if (-not $commitEntrega) { throw 'O historico ainda nao contem a entrega 1.1.' }
git restore --source=$commitEntrega --worktree -- package-lock.json
npm.cmd ci
if ($LASTEXITCODE -ne 0) { throw 'A instalacao pelo lockfile falhou.' }
```

`--all` pesquisa também as referências que ficaram à frente do commit-base após o `switch --detach`; sem essa opção, o histórico iniciado no ponto-base não encontraria a entrega posterior. A restauração recupera **somente** `package-lock.json`; o restante continua sendo o que você escreveu. `npm ci` exige manifests e lockfile coerentes e reinstala usando a árvore registrada. Ele remove `node_modules` existente antes de instalar; por isso o executamos na cópia de estudo descartável. A primeira execução real desta tarefa gerou o lockfile com `npm install`; o bloco Git acima ensina como leitores futuros encontram sua versão exata.

## Passo 7 — Compilar e conferir a API

Execute na raiz:

```powershell
npm.cmd run build
if ($LASTEXITCODE -ne 0) { throw 'O build falhou.' }
node --check api/src/app.js
if ($LASTEXITCODE -ne 0) { throw 'Sintaxe da API invalida.' }
node --input-type=module -e "import { createApp } from './api/src/app.js'; const app = createApp(); console.log(typeof app, typeof app.use);"
if ($LASTEXITCODE -ne 0) { throw 'A importacao da API falhou.' }
Get-ChildItem -Recurse web/dist
```

O script da raiz encaminha o build ao workspace web. Vite lê o HTML e percorre os módulos importados, transforma JSX e produz `web/dist/index.html` e arquivos CSS/JavaScript em `web/dist/assets/`. Esses recursos são o resultado compilado; mantenha o código-fonte como origem das alterações. Na entrega, foram transformados 16 módulos.

`node --check` verifica a sintaxe sem iniciar servidor. Já `--input-type=module -e` executa um pequeno programa ESM: importa a fábrica, cria a aplicação e consulta os tipos. O resultado esperado é `function function`, pois uma aplicação Express é chamável e oferece o método `use`. Isso verifica importação e criação, não endpoints inexistentes. Os arquivos da API não são incluídos no bundle do frontend.

## Problemas comuns

- **`EBADENGINE`:** confira `node --version` no mesmo terminal. O Node global 24.11.1 é antigo para este projeto. Ajuste o PATH da sessão com a distribuição portátil verificada; não desative `engine-strict` para ocultar a incompatibilidade.
- **`npm.ps1` bloqueado:** use `npm.cmd` conforme os comandos deste capítulo. Não é necessário reduzir a política global de execução.
- **Permissão negada no cache npm:** confirme o cache temporário de sessão indicado no passo 1. Não apague caches de outros projetos.
- **`npm ci` informa divergência de lockfile:** compare os três manifests com os blocos completos. O lockfile precisa corresponder a eles; não use `npm install` apenas para esconder uma alteração acidental se a intenção é reproduzir a entrega exata.
- **Tela vazia:** confira o console, `id="root"`, o caminho `/src/main.jsx` e as importações. Faça o build novamente após mudar arquivos; preview serve o build existente.
- **`vite` não encontrado:** instale pela raiz com dependências de desenvolvimento. O npm resolve os executáveis locais durante `npm run`; não é preciso instalar Vite globalmente.
- **Página indisponível depois de `createApp`:** a fábrica não abre porta. Use Vite para a página; o listener Express e as rotas serão implementados na próxima tarefa.
- **Checksum diferente ou download falhou:** interrompa a preparação do runtime e obtenha novamente os arquivos oficiais. Não trate uma tentativa com falha como verificação concluída.
