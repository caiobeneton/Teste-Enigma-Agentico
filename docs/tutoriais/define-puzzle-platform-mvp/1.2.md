# 1.2 — Encaminhar a API e entregar o build com Express

## Objetivo e ponto de partida

No [capítulo 1.1](1.1.md), Vite apresentava a página e a API era somente uma fábrica importável. Agora vamos iniciar Express, criar `GET /api/health`, encaminhar `/api` do Vite durante o desenvolvimento e servir o build pelo Express em produção local.

Você aprenderá por que a ordem dos middlewares importa, como distinguir navegação da SPA de arquivos ausentes e como localizar o build sem depender da pasta usada para iniciar o processo. **SPA** significa aplicação de página única: o servidor entrega um HTML de entrada e o JavaScript do navegador cuida da interface.

## Passo 2 — Encaminhar `/api` pelo Vite

### Arquivo `web/vite.config.js`

```javascript
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: { "/api": "http://localhost:3000" },
  },
});
```

Um **proxy** recebe a requisição e a encaminha a outro servidor. O navegador pede `/api/health` à origem do Vite; Vite repassa esse caminho ao Express na porta 3000 e devolve a resposta. O prefixo `/api` é preservado: não há `rewrite`.

Isso mantém a URL usada pelo navegador na mesma origem da página durante o desenvolvimento. Não precisamos introduzir configuração CORS para essa comunicação. A opção fica em `server`, portanto trata do servidor de desenvolvimento do Vite, conforme sua [documentação de proxy](https://vite.dev/config/server-options#server-proxy). Em produção local, o próprio Express servirá página e API.

**Como conferir depois:** a URL do Vite `/api/health` deverá responder com o JSON do Express. Ver somente a página abrir não comprova que o encaminhamento funciona.

## Passo 3 — Construir a aplicação na ordem correta

### Arquivo `api/src/app.js`

```javascript
import express from "express";
import { existsSync } from "node:fs";
import path from "node:path";
import { fileURLToPath } from "node:url";

const buildDirectory = fileURLToPath(new URL("../../web/dist/", import.meta.url));

export function createApp({ production = false } = {}) {
  const app = express();

  app.get("/api/health", (_req, res) => res.json({ status: "ok" }));
  app.use("/api", (_req, res) => res.status(404).json({ error: { code: "NOT_FOUND", message: "Recurso não encontrado." } }));

  if (production) {
    const index = path.join(buildDirectory, "index.html");
    if (!existsSync(index)) throw new Error("Build do frontend ausente; execute npm run build.");
    app.use(express.static(buildDirectory));
    app.use((req, res, next) => {
      const html = /(?:^|,)\s*text\/html\s*(?:;[^,]*)?(?:,|$)/i.test(req.get("accept") || "");
      if ((req.method === "GET" || req.method === "HEAD") && html && req.accepts("html") && !path.extname(req.path)) {
        return res.sendFile(index);
      }
      return next();
    });
  }

  return app;
}
```

### Localizar o build pelo módulo

`import.meta.url` identifica este arquivo JavaScript. `new URL("../../web/dist/", import.meta.url)` resolve a pasta do frontend a partir dele; `fileURLToPath` converte a URL em caminho do sistema operacional, inclusive no Windows. `path.join` acrescenta `index.html`.

Por que não usar `process.cwd()`? Ele é a pasta corrente do processo. Os scripts de workspace podem iniciar a API dentro de `api/`; um caminho relativo calculado pela pasta corrente poderia procurar o build no lugar errado. A localização do módulo permanece estável.

### Separar criação de execução

`createApp({ production = false } = {})` continua sendo uma fábrica. O objeto opcional escolhe se ela deve servir o build; sem argumento, cria a parte de API. Importar o módulo não chama `listen` nem abre porta. Isso permite fazer verificações isoladas e escolher uma porta temporária nos exemplos.

### Responder à API antes de considerar o frontend

Um **middleware** participa do processamento de uma requisição. Express os percorre na ordem em que foram registrados. Aqui, a sequência é:

```text
GET /api/health → JSON de saúde
demais pedidos sob /api → 404 JSON
em produção: arquivo real em web/dist → arquivo
em produção: navegação HTML elegível → index.html
o restante → 404 padrão do Express
```

`res.json({ status: "ok" })` gera uma resposta JSON mínima. O argumento `_req` indica que o handler não usa a requisição. A rota não informa banco, segredo, conta ou conteúdo: esses recursos ainda não existem.

Em seguida, `app.use("/api", ...)` captura o que não foi resolvido nesse prefixo, incluindo `/api`, uma rota desconhecida e um POST para `/api/health`. Mesmo que o cliente peça HTML, essa resposta será 404 JSON. Colocá-la antes dos estáticos impede que um erro de API vire a página do React.

### Servir arquivos e limitar o fallback da SPA

Quando `production` é verdadeiro, primeiro verificamos se o HTML foi compilado. Se estiver ausente, a criação falha com mensagem clara. O modo de desenvolvimento não exige o build porque Vite atende a página.

`express.static(buildDirectory)` procura arquivos reais: HTML, JavaScript, CSS e outros recursos existentes do build. O middleware seguinte é um **fallback**, um caminho alternativo para navegação direta a uma URL da SPA que não corresponde a um arquivo.

O fallback exige quatro condições:

1. O método é **GET ou HEAD**, operações de leitura. HEAD recebe cabeçalhos equivalentes, sem corpo de resposta.
2. O cabeçalho **Accept menciona explicitamente `text/html`**. A expressão regular encontra esse tipo entre itens separados por vírgulas e permite parâmetros.
3. `req.accepts("html")` confirma que HTML é aceito pela negociação de conteúdo. Isso impede aceitar `text/html;q=0`, cuja qualidade zero recusa esse tipo.
4. O caminho **não possui extensão** segundo `path.extname`. Assim, um arquivo ausente como `/ausente.js` não recebe HTML disfarçado de JavaScript.

As duas verificações de Accept são necessárias: usar apenas negociação poderia aceitar o curinga `*/*`; usar apenas a expressão regular poderia aceitar a menção com `q=0`. Combinadas, preservam o contrato desta etapa.

Quando as condições passam, `sendFile(index)` entrega a entrada da SPA. Caso contrário, `next()` deixa o Express produzir seu 404. Esse 404 fora de `/api` não usa o envelope JSON da API. A regra não comprova que a tela correspondente existe no React: `/nexo/novo` recebe o mesmo bootstrap, pois o roteamento funcional ainda será implementado.

O fallback usa middleware sem um padrão de rota curinga. Isso evita copiar a forma antiga `app.get("*", ...)`, incompatível com a sintaxe de caminhos do Express 5. Veja a [migração de caminhos](https://expressjs.com/en/guide/migrating-5.html#path-syntax) e a [referência do Express](https://expressjs.com/en/5x/api/).

## Passo 4 — Criar a entrada que abre a porta

### Arquivo `api/src/server.js`

```javascript
import { createApp } from "./app.js";

const production = process.env.NODE_ENV === "production";
const port = process.env.PORT || 3000;
const app = createApp({ production });
app.listen(port, () => console.log(`Servidor disponível em http://localhost:${port}`));
```

Esse arquivo tem a responsabilidade que a fábrica não tem: ler a configuração mínima e iniciar o servidor. Somente o valor exato `production` ativa estáticos e fallback. `PORT` escolhe a porta quando fornecida; na ausência dela, usamos 3000, destino do proxy de desenvolvimento.

Esta é uma configuração intermediária. Validação central de ambiente, origem, dados e segredo pertence à tarefa 1.3. Um teste em modo de produção local nesta aula não equivale a publicar o piloto com HTTPS, persistência e autenticação.

Abra o endereço informado pelo Vite. A porta usual é 5173, mas ele pode escolher outra se estiver ocupada. Para fixá-la durante a verificação, em vez do último comando use diretamente o workspace:

## Passo 7 — Compilar e testar a entrega integrada

Na raiz, sem outro processo ocupando a porta 3000:

```powershell

$env:NODE_ENV = 'production'
$env:PORT = '3000'
npm.cmd start
```

Abra `http://localhost:3000/` e depois uma navegação direta como `http://localhost:3000/rota-direta`. O navegador pede HTML e recebe o build. A pergunta deve continuar “O que você busca?”, com título `Nexo`. Essa navegação não é uma nova tela funcional.

O gerente inspecionou `/rota-direta` no Chrome e confirmou a pergunta e console sem erros; encerrou a aba e o processo. O programador verificou os contratos HTTP e o proxy com requisições reais. Teste HTTP e inspeção de navegador são evidências diferentes.

Para reproduzir os contratos em uma verificação isolada, execute o bloco abaixo na raiz **depois do build**. Ele cria uma instância temporária em uma porta escolhida pelo sistema e a fecha ao terminar; não deixa um servidor em segundo plano:

```powershell
@'
import assert from "node:assert/strict";
import { once } from "node:events";
import { createApp } from "./api/src/app.js";

const server = createApp({ production: true }).listen(0, "127.0.0.1");
await once(server, "listening");
const origem = `http://127.0.0.1:${server.address().port}`;
const casos = [
  ["GET", "/api/health", "text/html", 200, "json"],
  ["GET", "/api/inexistente", "text/html", 404, "json"],
  ["GET", "/api", "text/html", 404, "json"],
  ["POST", "/api/health", "text/html", 404, "json"],
  ["GET", "/nexo/novo", "text/html", 200, "html"],
  ["HEAD", "/nexo/novo", "text/html", 200, "vazio"],
  ["GET", "/ausente.js", "text/html", 404, "outro"],
  ["GET", "/assets/ausente.js", "text/html", 404, "outro"],
  ["GET", "/nexo/novo", "*/*", 404, "outro"],
  ["GET", "/nexo/novo", "text/html;q=0", 404, "outro"],
  ["POST", "/nexo/novo", "text/html", 404, "outro"],
];

try {
  for (const [method, caminho, accept, status, tipo] of casos) {
    const r = await fetch(origem + caminho, { method, headers: { accept } });
    const texto = await r.text();
    assert.equal(r.status, status, `${method} ${caminho} Accept=${accept}`);
    if (tipo === "json") {
      assert.match(r.headers.get("content-type"), /application\/json/);
      const valor = JSON.parse(texto);
      if (status === 200) assert.deepEqual(valor, { status: "ok" });
      else assert.equal(valor.error.code, "NOT_FOUND");
    } else if (tipo === "html") {
      assert.match(r.headers.get("content-type"), /text\/html/);
      assert.match(texto, /id="root"/);
    } else if (tipo === "vazio") {
      assert.equal(texto, "");
    } else {
      assert.ok(!texto.includes('id="root"'), "O erro nao deve entregar a SPA");
    }
    console.log(method, caminho, accept, "=>", r.status);
  }
  const pagina = await (await fetch(origem + "/")).text();
  const recurso = pagina.match(/src="([^"]+\.js)"/)[1];
  const js = await fetch(origem + recurso);
  assert.equal(js.status, 200);
  assert.match(js.headers.get("content-type"), /javascript/);
  console.log("Recurso real do build =>", js.status);
} finally {
  await new Promise((resolve, reject) => server.close(erro => erro ? reject(erro) : resolve()));
}
'@ | node --input-type=module
```

`listen(0)` solicita uma porta disponível; `once` aguarda o servidor estar pronto. `assert` interrompe a verificação se um resultado divergir. O `finally` fecha a instância mesmo se uma asserção falhar. O bloco verifica status e conteúdo, incluindo a ausência da SPA em erros; ele não é uma suíte de jogo nem substitui a inspeção visual.

## Passo 8 — Confirmar que a pasta de execução não altera o build

Ainda na raiz, execute esta segunda verificação curta:

```powershell
@'
import assert from "node:assert/strict";
import { once } from "node:events";
import { tmpdir } from "node:os";
import { pathToFileURL } from "node:url";
import path from "node:path";

const modulo = pathToFileURL(path.resolve("api/src/app.js")).href;
const pastaAnterior = process.cwd();
process.chdir(tmpdir());
const { createApp } = await import(modulo);
const server = createApp({ production: true }).listen(0, "127.0.0.1");
await once(server, "listening");
try {
  const r = await fetch(`http://127.0.0.1:${server.address().port}/nexo/novo`, { headers: { accept: "text/html" } });
  assert.equal(r.status, 200);
  assert.match(await r.text(), /id="root"/);
  console.log("HTML entregue a partir de outro diretorio =>", r.status);
} finally {
  await new Promise((resolve, reject) => server.close(erro => erro ? reject(erro) : resolve()));
  process.chdir(pastaAnterior);
}
'@ | node --input-type=module
```

Primeiro transformamos o caminho absoluto do módulo em URL. Depois mudamos apenas a pasta do processo temporário para o diretório temporário do sistema e importamos a fábrica. A resposta 200 demonstra que o caminho do build vem do módulo, não do diretório corrente. A pasta do seu PowerShell não muda: `process.chdir` afeta esse processo Node.

## Problemas comuns

- **`Build do frontend ausente`:** execute `npm.cmd run build` antes de ativar o modo de produção. Não crie um HTML vazio apenas para evitar a falha.
- **`EADDRINUSE`:** a porta já está ocupada. Encerre o processo de estudo anterior com `Ctrl+C`. Se mudar a porta da API no desenvolvimento, o destino do proxy também precisa corresponder; a validação central será tratada na tarefa 1.3.
- **Proxy retorna erro de conexão:** confirme que a API está ativa na porta 3000 e que consultou o endereço/porta atuais do Vite.
- **API funciona, mas navegação não entrega o build:** confira se `NODE_ENV` é exatamente `production`. O modo padrão serve a API; Vite atende o frontend no desenvolvimento.
- **Um pedido fetch à rota SPA recebe 404:** `fetch` sem Accept explícito normalmente pede `*/*`. O contrato do fallback exige HTML; use o cabeçalho nos exemplos. Isso não deve afetar uma rota de API válida, que tem seu tratamento próprio.
- **Arquivo `.js` ausente recebe 404:** esperado. Devolver HTML esconderia a causa e produziria erro de módulo no navegador.
- **Navegação direta mostra apenas a pergunta inicial:** esperado nesta base. A entrega do HTML não implementa React Router, formulários ou o jogo.
- **Flags de Vite não chegaram ao destino:** use o comando direto do workspace mostrado no passo 6. O script da raiz permanece indicado para a execução sem argumentos extras.
