# 1.3 — Validar configuração antes de iniciar o servidor

## Objetivo e ponto de partida

No [capítulo 1.2](1.2.md), o servidor lia porta e modo diretamente de `process.env`. Agora vamos transformar essas entradas em uma configuração validada, conferir o diretório destinado aos dados, proteger arquivos locais no Git e executar testes reais. Também criaremos o comando de migração com um limite explícito: ele **falha informando a dependência da tarefa 2.1**, pois SQLite ainda não foi implementado.

O commit-base é `649abba2daf3b65bcf7dc5a7aeee95384389a91d`, entrega da tarefa 1.2. Leia seu tutorial e o [registro 1.3](../../registros/define-puzzle-platform-mvp/1.3.md) antes de começar. O trabalho é de infraestrutura; não modifica interface e dispensa o designer conforme o fluxo.

Uma variável de ambiente chega ao processo como texto. Sem validação, uma porta como `123abc`, uma origem com credenciais ou um caminho relativo poderiam chegar ao ponto de execução sem corresponder à intenção do operador. Vamos rejeitar essas entradas **antes de criar a aplicação e abrir a porta**.

## Passo 2 — Definir o contrato de cada variável

Antes do código, separe valores padrão de desenvolvimento de requisitos de produção:

| Variável | Desenvolvimento/teste | Produção e motivo |
| --- | --- | --- |
| `NODE_ENV` | Padrão `development`; aceita também `test`. | Somente `production` ativa o modo de entrega integrada; nomes desconhecidos são recusados. |
| `PORT` | Padrão 3000. | Inteiro decimal de 1 a 65535, sem texto parcialmente numérico. A porta 0 é reservada aos testes que escolhem porta dinâmica diretamente. |
| `APP_ORIGIN` | Padrão `http://localhost:5173`; host deve ser local. | Obrigatória e HTTPS, sem credenciais, caminho, query ou fragmento. É uma origem, não uma URL de página. |
| `DATABASE_PATH` | Padrão absoluto em `data/nexo.sqlite`, relativo à localização do módulo. | Caminho absoluto explícito para um arquivo cujo diretório pai já exista e seja gravável. Não substituir por um local temporário se estiver errado. |
| `SESSION_SECRET` | Opcional nesta etapa, sem sessão implementada. | Valor não vazio nem só espaços, preservado como fornecido. Recomenda-se gerar um valor longo e aleatório e conservá-lo entre reinícios. |

**Origem** é a combinação de protocolo, host e porta, como `https://example.test`. `https://example.test/conta` contém também um caminho e não atende ao contrato. Em desenvolvimento/teste, os hosts aceitos pelo código serão `localhost`, `127.0.0.1` e `[::1]`.

Validar `APP_ORIGIN` ainda não aplica proteção de origem às mutações. Da mesma forma, validar caminho e segredo não cria banco nem sessão. A configuração prepara contratos que as tarefas seguintes vão consumir.

## Passo 3 — Separar leitura validada de verificação de armazenamento

### Arquivo `api/src/config.js`

```javascript
import path from "node:path";
import { fileURLToPath } from "node:url";
import { accessSync, constants, mkdirSync, mkdtempSync, rmdirSync, statSync, existsSync } from "node:fs";

const defaultDataDirectory = fileURLToPath(new URL("../../data/", import.meta.url));

export function loadConfig(env) {
  const mode = env.NODE_ENV === undefined ? "development" : env.NODE_ENV;
  if (!["development", "test", "production"].includes(mode)) throw new Error("NODE_ENV deve ser development, test ou production.");
  const rawPort = env.PORT === undefined ? "3000" : env.PORT;
  if (!/^\d+$/.test(rawPort) || Number(rawPort) < 1 || Number(rawPort) > 65535) throw new Error("PORT deve ser inteiro entre 1 e 65535.");
  const production = mode === "production";
  const rawOrigin = env.APP_ORIGIN === undefined && !production ? "http://localhost:5173" : env.APP_ORIGIN;
  let origin;
  try { origin = new URL(rawOrigin); } catch { throw new Error("APP_ORIGIN deve ser uma origem válida."); }
  if (origin.username || origin.password || origin.pathname !== "/" || origin.search || origin.hash || !["http:", "https:"].includes(origin.protocol)) throw new Error("APP_ORIGIN deve conter somente uma origem HTTP(S).");
  if (production && origin.protocol !== "https:") throw new Error("APP_ORIGIN deve usar HTTPS em produção.");
  if (!production && !["localhost", "127.0.0.1", "[::1]"].includes(origin.hostname)) throw new Error("APP_ORIGIN deve ser local em desenvolvimento e teste.");
  const databasePath = env.DATABASE_PATH === undefined && !production ? path.join(defaultDataDirectory, "nexo.sqlite") : env.DATABASE_PATH;
  if (!databasePath || !path.isAbsolute(databasePath) || /[\\/]$/.test(databasePath)) throw new Error("DATABASE_PATH deve ser um caminho absoluto para arquivo.");
  if (process.platform === "win32") {
    const parts = databasePath.slice(path.parse(databasePath).root.length).split(/[\\/]/);
    const invalid = parts.some(part => /[<>:"|?*\x00-\x1f]/.test(part) || /[. ]$/.test(part) || /^(con|prn|aux|nul|com[1-9]|lpt[1-9])(?:\.|$)/i.test(part));
    if (invalid) throw new Error("DATABASE_PATH contém nome de arquivo ou diretório inválido no Windows.");
  }
  if (production && (!env.SESSION_SECRET || !env.SESSION_SECRET.trim())) throw new Error("SESSION_SECRET é obrigatório em produção.");
  return { mode, port: Number(rawPort), origin: origin.origin, databasePath, sessionSecret: env.SESSION_SECRET };
}

export function validateStorage(config) {
  const directory = path.dirname(config.databasePath);
  try {
    if (config.mode !== "production" && directory === defaultDataDirectory.replace(/[\\/]$/, "")) mkdirSync(directory, { recursive: true });
    if (!statSync(directory).isDirectory()) throw new Error();
    accessSync(directory, constants.W_OK);
    if (existsSync(config.databasePath) && !statSync(config.databasePath).isFile()) throw new Error();
    const probe = mkdtempSync(path.join(directory, ".nexo-write-check-"));
    rmdirSync(probe);
  } catch { throw new Error("DATABASE_PATH exige arquivo e diretório pai existente e gravável."); }
}
```

### Por que receber `env` como argumento

`loadConfig` não lê `process.env` escondido dentro dela, não modifica esse objeto nem acessa o disco. O chamador fornece um objeto; a função devolve configuração ou lança um erro. Isso permite testar cada situação com objetos pequenos e sem alterar o ambiente global dos outros testes.

O teste `=== undefined` aplica padrão somente quando a variável está ausente. Uma string vazia explicitamente configurada não é a mesma coisa que ausência e, conforme a variável, será rejeitada. A expressão regular da porta exige todos os caracteres numéricos; depois `Number` converte o valor e a faixa elimina zero e números grandes.

`new URL` interpreta a origem, enquanto as verificações seguintes restringem o resultado. Não usamos `startsWith("https")`, que não descreve corretamente uma URL. Ao retornar `origin.origin`, guardamos sua representação de origem, sem adicionar um caminho.

No Windows, ser absoluto não torna um caminho válido. O bloco `win32` retira a raiz (como `C:\`) antes de examinar cada componente e recusa caracteres reservados, sufixo com ponto/espaço e nomes de dispositivos como `CON` ou `NUL`. Assim, `nexo?.sqlite` é rejeitado antes de qualquer tentativa futura de abrir banco. A [documentação de nomes no Windows](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file) explica essas restrições; o código torna explícito o conjunto verificado nesta etapa.

O segredo passa por `trim()` apenas para detectar conteúdo formado somente por espaços. O retorno usa **o valor original**, sem normalizá-lo. As mensagens nomeiam variáveis e regras, sem imprimir seus valores. Tamanho e aleatoriedade continuam uma responsabilidade de geração; o código não finge medir entropia contando caracteres.

### Por que o disco fica em outra função

`validateStorage` tem efeitos externos deliberados. Ela pode criar **somente o diretório padrão de desenvolvimento/teste**. Em produção ou em um caminho personalizado, o operador deve preparar o diretório pai; o programa não escolhe outro lugar silenciosamente.

`statSync` verifica o tipo de diretório e, se o destino já existir, se ele é arquivo. `accessSync(..., W_OK)` consulta permissão de escrita. `mkdtempSync` tenta criar uma pasta com nome exclusivo dentro do pai, e `rmdirSync` remove apenas essa pasta de sondagem vazia. Isso verifica a capacidade de criar uma entrada sem abrir ou tocar no banco futuro. A [API de arquivos do Node](https://nodejs.org/docs/latest-v24.x/api/fs.html#fsmkdtempsyncprefix-options) fornece essas operações.

Essa conferência do diretório não comprova que um banco existente possa ser aberto pelo SQLite nem que sua estrutura esteja correta. Conexão e migrações virão na 2.1. O caminho padrão usa a localização do módulo, mantendo a independência de diretório de execução ensinada na 1.2.

## Passo 4 — Validar antes de abrir a porta

### Arquivo `api/src/server.js`

```javascript
import { createApp } from "./app.js";
import { loadConfig, validateStorage } from "./config.js";

try {
  const config = loadConfig(process.env);
  validateStorage(config);
  const app = createApp({ production: config.mode === "production" });
  app.listen(config.port, () => console.log(`Servidor disponível em http://localhost:${config.port}`));
} catch (error) {
  console.error(error.message);
  process.exitCode = 1;
}
```

A ordem agora é: validar valores → conferir diretório → criar aplicação → `listen`. Um erro de configuração interrompe o caminho antes de aceitar requisições.

O `catch` trata erros síncronos dessas etapas e mostra somente sua mensagem. `process.exitCode = 1` informa falha ao sistema quando o processo terminar; não é um sucesso que apenas escreveu um aviso. A [documentação de processos do Node](https://nodejs.org/docs/latest-v24.x/api/process.html#processexitcode) explica esse código de saída. Isso não substitui tratamento de eventos assíncronos futuros ou validações das próximas funcionalidades.

## Passo 5 — Manter porta da API e proxy coerentes

### Arquivo `web/vite.config.js`

```javascript
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: { "/api": `http://localhost:${process.env.PORT || "3000"}` },
  },
});
```

Na 1.2, o destino era fixo em 3000. Agora Vite consulta `PORT` no seu próprio processo. Portanto, configure a mesma porta nos **dois terminais**, Vite e API. A validação rigorosa da porta é feita pelo módulo da API; essa linha apenas mantém o destino do proxy alinhado. A [opção de proxy do Vite](https://vite.dev/config/server-options#server-proxy) continua preservando `/api`, sem rewrite.

`APP_ORIGIN` é uma configuração da aplicação, não uma ordem para o Vite mudar sua porta. O padrão local é `http://localhost:5173`; se optar por outra origem de frontend, ajuste-a conscientemente. Nenhuma política de CORS ampla foi adicionada.

## Passo 8 — Escrever testes de valor, processo e HTTP

### Arquivo `api/test/config.test.js`

```javascript
import test from "node:test";
import assert from "node:assert/strict";
import { mkdtempSync, rmSync } from "node:fs";
import os from "node:os";
import path from "node:path";
import { spawnSync } from "node:child_process";
import { fileURLToPath } from "node:url";
import { loadConfig, validateStorage } from "../src/config.js";
import { createApp } from "../src/app.js";

const serverFile = fileURLToPath(new URL("../src/server.js", import.meta.url));
const migrateFile = fileURLToPath(new URL("../src/migrate.js", import.meta.url));
const dir = mkdtempSync(path.join(os.tmpdir(), "nexo-config-test-"));
const valid = { NODE_ENV: "production", PORT: "4321", APP_ORIGIN: "https://example.test", DATABASE_PATH: path.join(dir, "test.sqlite"), SESSION_SECRET: "test-secret-value" };
test.after(() => rmSync(dir, { recursive: true, force: true }));

test("valida ambiente sem alterar segredo", () => {
  assert.equal(loadConfig({}).port, 3000);
  assert.equal(loadConfig(valid).sessionSecret, valid.SESSION_SECRET);
  for (const [env, variable] of [
    [{...valid, NODE_ENV: "unknown"}, "NODE_ENV"],
    [{...valid, PORT: "123abc"}, "PORT"],
    [{...valid, PORT: "0"}, "PORT"],
    [{...valid, PORT: "65536"}, "PORT"],
    [{...valid, APP_ORIGIN: "http://example.test"}, "APP_ORIGIN"],
    [{...valid, APP_ORIGIN: "https://example.test/path"}, "APP_ORIGIN"],
    [{...valid, APP_ORIGIN: "https://user:pass@example.test"}, "APP_ORIGIN"],
    [{...valid, DATABASE_PATH: "relative.sqlite"}, "DATABASE_PATH"],
    [{...valid, SESSION_SECRET: " "}, "SESSION_SECRET"],
  ]) assert.throws(() => loadConfig(env), new RegExp(variable));
  assert.throws(() => loadConfig({NODE_ENV: "production"}), /APP_ORIGIN/);
  assert.throws(() => validateStorage(loadConfig({...valid, DATABASE_PATH: path.join(dir,"missing","test.sqlite")})), /DATABASE_PATH/);
  assert.throws(() => validateStorage(loadConfig({...valid, DATABASE_PATH: dir})), /DATABASE_PATH/);
  validateStorage(loadConfig(valid));
});

test("configurações inválidas encerram processo antes de ouvir e não revelam segredo", () => {
  for (const [overrides, variable] of [
    [{NODE_ENV: "invalid"}, "NODE_ENV"],
    [{PORT: "invalid"}, "PORT"],
    [{APP_ORIGIN: "http://example.test"}, "APP_ORIGIN"],
    [{DATABASE_PATH: "relative.sqlite"}, "DATABASE_PATH"],
    [{SESSION_SECRET: " "}, "SESSION_SECRET"],
    [{DATABASE_PATH: path.join(dir, "missing", "file.sqlite")}, "DATABASE_PATH"],
  ]) {
    const child = spawnSync(process.execPath, [serverFile], {env: {...process.env, ...valid, ...overrides}, encoding: "utf8", timeout: 3000});
    assert.ifError(child.error);
    assert.notEqual(child.status, 0);
    assert.match(child.stderr, new RegExp(variable));
    assert.doesNotMatch(child.stderr + child.stdout, /test-secret-value|Servidor disponível/);
  }
});

test("nome de arquivo inválido no Windows falha antes de abrir porta", {skip: process.platform !== "win32"}, () => {
  const child = spawnSync(process.execPath, [serverFile], {
    env: {...process.env, ...valid, DATABASE_PATH: path.join(dir, "nexo?.sqlite")},
    encoding: "utf8", timeout: 3000,
  });
  assert.ifError(child.error);
  assert.notEqual(child.status, 0);
  assert.match(child.stderr, /DATABASE_PATH/);
  assert.doesNotMatch(child.stderr + child.stdout, /test-secret-value|Servidor disponível/);
});

test("migração pendente informa a tarefa 2.1 e falha", () => {
  const child = spawnSync(process.execPath, [migrateFile], {encoding: "utf8", timeout: 3000});
  assert.ifError(child.error);
  assert.notEqual(child.status, 0);
  assert.match(child.stderr, /2\.1/);
});

test("servidor de produção mantém contratos HTTP", async () => {
  const config = loadConfig(valid);
  validateStorage(config);
  const server = createApp({production: true}).listen(0, "127.0.0.1");
  await new Promise(resolve => server.once("listening", resolve));
  try {
    const base = `http://127.0.0.1:${server.address().port}`;
    const health = await fetch(base + "/api/health");
    assert.equal(health.status, 200);
    assert.deepEqual(await health.json(), {status: "ok"});
    const missing = await fetch(base + "/api/ausente", {headers:{accept:"text/html"}});
    assert.equal(missing.status, 404);
    assert.match(missing.headers.get("content-type"), /application\/json/);
    assert.equal((await fetch(base + "/nexo/novo", {headers:{accept:"text/html"}})).status, 200);
    assert.equal((await fetch(base + "/ausente.js", {headers:{accept:"text/html"}})).status, 404);
    assert.equal((await fetch(base + "/nexo/novo", {headers:{accept:"*/*"}})).status, 404);
  } finally { await new Promise(resolve => server.close(resolve)); }
});
```

Há cinco testes, com várias situações dentro deles:

1. **Valores e armazenamento:** verifica padrões, segredo preservado, entradas recusadas e diretório inexistente ou destino que é diretório. A pasta temporária é exclusiva do teste; a limpeza registrada em `test.after` remove apenas esse local.
2. **Processo filho inválido:** `spawnSync` executa o servidor com o mesmo Node de `process.execPath`, substituindo uma variável por vez. Confere saída não zero, nome da variável e ausência tanto do segredo fictício quanto da mensagem de servidor disponível. A ordem do código garante que a validação vem antes do `listen`; a verificação do processo confirma o encerramento sem anúncio de inicialização.
3. **Nome inválido no Windows:** um subprocesso com `nexo?.sqlite` deve falhar antes de anunciar servidor. O caso é ignorado em outras plataformas, pois valida uma restrição específica do Windows.
4. **Migração pendente:** executa seu ponto de entrada e espera falha mencionando 2.1. Um teste passar aqui significa que o bloqueio foi corretamente comunicado, não que houve migração.
5. **Contratos HTTP reais:** cria uma aplicação em porta dinâmica, confere saúde, JSON 404 e condições do fallback e fecha o servidor em `finally`.

Os processos de falha e migração têm timeout de 3000ms. Se uma regressão fizer o servidor continuar ativo, a verificação não fica aguardando indefinidamente; `assert.ifError(child.error)` também impede confundir um timeout ou falha de execução com a rejeição esperada de configuração.

`test-secret-value` e a URL com `user:pass` são dados fictícios do teste, nunca credenciais de implantação. O teste HTTP usa a fábrica após validar uma configuração; não inicia o módulo de servidor de produção como um processo válido completo. A verificação manual do programador no registro cobre também esse caminho de inicialização.

O [executor nativo do Node](https://nodejs.org/docs/latest-v24.x/api/test.html) descobre `api/test/config.test.js` quando o script roda no workspace. As asserções devem falhar quando houver divergência real; não criamos um comando que apenas imprime sucesso.

O build deve transformar 16 módulos e os cinco testes devem passar no Windows; o caso específico dessa plataforma é ignorado em outros sistemas. O teste HTTP depende do build real da 1.2, por isso compilamos antes. `migrate` deve mostrar a mensagem de dependência e terminar com código não zero. Não registre isso como aplicação de esquema.

`git check-ignore` confirma que os três exemplos seriam ignorados sem precisar criá-los. Confira também os novos arquivos de código; `diff --check` não substitui sua revisão nem verifica por si só a presença de segredo real.

## Passo 10 — Executar exemplos válidos e manter o proxy alinhado

Em um terminal novo, prepare Node e entre na raiz da cópia. Para desenvolvimento, sem carregar variáveis de uma tentativa anterior de produção:

```powershell

$env:PORT = '3098'
$env:APP_ORIGIN = 'http://localhost:5173'
Remove-Item Env:DATABASE_PATH -ErrorAction SilentlyContinue
Remove-Item Env:SESSION_SECRET -ErrorAction SilentlyContinue
npm.cmd run dev:api
```

O padrão local cria `data/` se necessário e verifica escrita, mas **não cria `nexo.sqlite`**. Em outro terminal com o mesmo runtime:

```powershell
$env:PORT = '3098'
npm.cmd run dev --workspace=@nexo/web -- --host 127.0.0.1 --port 5173 --strictPort
```

Consulte a API diretamente e pelo Vite a partir de um terceiro terminal preparado:

```powershell
node --input-type=module -e "for (const url of ['http://127.0.0.1:3098/api/health','http://127.0.0.1:5173/api/health']) { const r = await fetch(url); console.log(r.status, await r.text()); }"
```

Ambos devem responder 200 com `{"status":"ok"}`. O programador confirmou essa combinação real de porta 3098/proxy 5173 nesta entrega, usando também uma instância com configuração válida de produção. Encerre processos com `Ctrl+C`; não deixe servidores de estudo ocupando portas.

Para exercitar a **validação de produção local**, após o build e sem outro processo na porta escolhida:

```powershell
$dadosAula = Join-Path $env:TEMP ('nexo-dados-aula-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $dadosAula | Out-Null
$env:NODE_ENV = 'production'
$env:PORT = '3098'
$env:APP_ORIGIN = 'https://example.test'
$env:DATABASE_PATH = Join-Path $dadosAula 'nexo.sqlite'
$env:SESSION_SECRET = node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
npm.cmd start
```

O comando gera um segredo descartável em memória e o atribui à variável, sem pedir que você copie um segredo real. Não publique nem imprima seu valor. Em uma implantação futura, gere e armazene um segredo próprio, longo e estável; não gere outro a cada reinício quando sessões reais passarem a depender dele.

`https://example.test` é uma origem fictícia para validar configuração. O Express deste capítulo continua atendendo **HTTP local**, sem criar certificado ou redirecionamento HTTPS. A pasta TEMP é só exemplo descartável de aula; o piloto exigirá local persistente e infraestrutura adequados. Nenhum arquivo SQLite é criado por este exemplo ainda.

## Problemas comuns

- **Produção falha com `APP_ORIGIN`:** forneça uma origem HTTPS explícita, sem credenciais, caminho, consulta ou fragmento. Não use a URL de uma tela.
- **`DATABASE_PATH` recusado:** use caminho absoluto para arquivo e confira se o pai existe e pode receber escrita. Não passe uma pasta como destino nem troque silenciosamente para TEMP em uma implantação.
- **Porta inválida:** use inteiro decimal de 1 a 65535. Porta 0 fica apenas nos testes de fábrica que pedem porta dinâmica ao sistema.
- **Variável está no `.env`, mas não foi lida:** nesta implementação não há carregamento automático. Defina `$env:NOME` no processo do PowerShell que iniciará a API.
- **API responde diretamente, mas proxy falha:** confirme `PORT` nos dois terminais. Mudar uma variável depois de o processo iniciar não altera o ambiente daquele processo.
- **Teste HTTP falha por build ausente:** rode `npm.cmd run build` antes de `npm.cmd test`; não substitua o HTML por uma fixture falsa.
- **`migrate` retorna erro:** é o comportamento pendente explícito até a 2.1, não uma migração bem-sucedida. Confira a mensagem e mantenha essa distinção no registro.
